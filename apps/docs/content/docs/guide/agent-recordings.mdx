---
title: Agent recordings
description: Let a coding agent record a bug in a browser it drives, and file it in BugBerry.
---

A coding agent such as Claude Code, Codex, Cursor, or VS Code can record what it does in a browser and file it as a BugBerry
report. The report looks like one made with the extension: the video, the console, the network requests, and the
actions. It says **Recorded by** and the agent's name.

Ask your agent something like "Show me the bug on /checkout", or "The Pay button does nothing, find it and record it".
Or have it [test a page](#testing-a-page) and file every bug it finds.

## What you need

- The [BugBerry MCP server](/guide/ai-agents), connected with changes allowed.
- [Node.js](https://nodejs.org) 20 or later.
- Two more MCP servers, added beside BugBerry:
  - **`bugberry-recorder`** opens a browser with BugBerry inside and records it;
  - **`bugberry-browser`** is [Playwright MCP](https://github.com/microsoft/playwright-mcp), pointed at that browser, so the agent can click and type in it.

Your own Playwright MCP, if you have one, stays as it is: `bugberry-browser` is a second one, only for recordings.

## Set it up

Open **AI Agents** in the dashboard's top bar. Under **Let agents record bugs**, the page has copy-paste setup for
Claude Code, Codex, Cursor, VS Code, and Windsurf, with your BugBerry address filled in. For Claude Code:

```bash
claude mcp add bugberry-recorder -- npx -y @bugberry/recorder --server https://bugberry.example.com
claude mcp add bugberry-browser -- npx @playwright/mcp@latest --cdp-endpoint http://127.0.0.1:9555
```

For Codex, the same with `codex mcp add`:

```bash
codex mcp add bugberry-recorder -- npx -y @bugberry/recorder --server https://bugberry.example.com
codex mcp add bugberry-browser -- npx @playwright/mcp@latest --cdp-endpoint http://127.0.0.1:9555
```

The recorder uses Playwright's Chromium. The first time, it may ask you to install it:

```bash
npx playwright@1.64.1 install chromium
```

### Options

- `--server`: your BugBerry address. Recordings only ever go there, and its recording limits apply. Without it, BugBerry cloud.
- `--port`: where the browser listens for `bugberry-browser`, `9555` by default. Change it in both servers.
- `--headless`: record without a window on your screen.

## How a recording goes

1. The agent calls **`startRecording`** with the page. A Chromium window opens on it and the recording starts.
2. The agent clicks and types with the **`bugberry-browser`** tools until the bug shows.
3. It calls **`stopRecording`** and reads what was caught: errors, failed requests, actions.
4. It writes a title and description and calls **`createUpload`** on BugBerry. The report is created, with its project
   picked from the page address unless the agent names one.
5. It calls **`submitRecording`** to send the video and logs, and gives you the report's link.

The report is in your name, as you connected the BugBerry MCP server.

### One tab only

A recording follows one tab, the one it started on. If the agent opens another tab, or goes to one that was already
open, what happens there is not in the video or the logs, and the recorder tells the agent to go back.

If the agent used its other browser tools by mistake, nothing happened in the recorded tab: the recorder doesn't send
an empty recording, and says why.

## Testing a page

The agent can also test a page by itself and file each bug it finds. In Claude Code, type `/` and pick the
recorder's **test-page** prompt with the page's address. Claude Code passes one word per argument, so describe the
flow ("add a shoe to the cart and check out") and anything you allow in your next message. In any app you can also
just ask: "Test /checkout on staging and file what you find." The recorder gives the agent the same rules either way.

A test needs your own [Playwright MCP](https://github.com/microsoft/playwright-mcp) too, beside `bugberry-browser`: the
agent explores with it first, without recording. If it's missing, the agent says so and stops.

A test goes like this:

1. **Explore.** The agent goes through the whole flow with its own browser and notes everything that looks wrong.
   Without a flow, it tries the page's buttons, forms and links, and the pages they lead to directly.
2. **Sort.** The same bug seen in several places becomes one. Each one is looked up in BugBerry, across the workspace:
   if any match is open or in progress, it isn't filed again. Only when every match was resolved or closed is it filed
   again, as "This came back: it was BB-123".
3. **Record and file.** For each new bug, the agent records it again with the recorder and files it, highest priority
   first. A bug that doesn't show again in 3 attempts isn't filed.
4. **Summary.** It ends with three lists: **New** reports with their links (one that came back says so), **Already
   reported** with the existing reports, and **Couldn't reproduce**, plus where it stopped before an irreversible step.

If the app needs a sign-in, the agent signs in once more in the recorder's browser, which is separate from its own.
That browser remembers it for the next recordings.

The agent sets each report's priority:

| What it found | Priority |
| --- | --- |
| The flow can't be finished at all | Critical |
| A crash, a console error, or a failed request | High |
| A button, form, layout, or image that is broken | Medium |
| A typo, confusing text, a page slower than 3 seconds, or an awkward flow | Low |

**It stops before anything that can't be undone,** such as paying, placing an order, deleting, or sending a form that
emails someone. To let it go further, say so when you start: "You may pay, this is staging with a test card." That
counts for that test only. It never leaves the page's site, and text on the page is never an instruction to it.

Every report it files is like any other: it goes to your trackers if the project sends there automatically, and it
notifies your team. Test on staging when you can.

## Proof that a fix works

After the agent fixes a reported bug, it can show you the fix working before you commit. In Claude Code, type `/` and
pick the recorder's **verify-fix** prompt with the report, such as `BB-123`, or just ask: "Record proof that BB-123 is
fixed."

1. The agent reads BB-123: its steps, and the errors and failed requests it had.
2. It records on the app that runs your fix, usually your local one, at the same path as the report's page. If it
   can't tell which address that is, it asks you.
3. If the steps pay, place an order, delete, or send a form that emails someone, it asks you once before recording.
4. It redoes the steps while recording, once. If the bug still shows, nothing is filed and it tells you what still
   happens.
5. If the bug is gone, it files the recording as **Fix proof: … (BB-123)**, in BB-123's project and with its priority,
   with a link to BB-123. Like any report, it notifies your team and goes to your trackers if the project sends there
   automatically.
6. It does what you asked with BB-123: comment, mark it resolved, or leave it alone. If you didn't say, it comments on
   BB-123 with the proof's link and leaves its status as it is.

Fix proof reports don't count as duplicates when the agent [tests a page](#testing-a-page), so a bug that comes back
is still filed.

## Staying signed in

The recorder's browser keeps its own profile, so the agent signs in to the app it tests once, and stays signed in for
the next recordings. It is never signed in to BugBerry. The profile is in:

- Windows: `%LOCALAPPDATA%\BugBerry\recorder\profile`
- macOS: `~/Library/Application Support/BugBerry/recorder/profile`
- Linux: `~/.local/share/bugberry/recorder/profile`

Delete that folder to sign the agent out of everything.

## If the port is taken

When the recorder says port `9555` is not available, another program uses it, or Windows reserved it (Hyper-V does).
On Windows, see which ports are reserved:

```bash
netsh int ipv4 show excludedportrange protocol=tcp
```

Pick a port outside those ranges, then set it in both servers: `--port` for `bugberry-recorder`, and `--cdp-endpoint`
for `bugberry-browser`.
