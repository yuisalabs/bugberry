The sign-in page shows only the methods you configure. Each is optional, but at least one must be on; the server refuses to start without one.

<Screenshot src="/screenshots/self-host/sign-in.png" alt="The sign-in page with Google and email codes on: Continue with Google, then Work email and Continue" />

The rules are the same for every method: the email must be verified, and when `ALLOWED_EMAIL_DOMAINS` is set, only those domains can sign in. The same person with the same verified email always lands in the same account, whichever method they use.

A provider is on when both its client ID and secret are set. Setting only one of them is an error.

## Google

1. In the Google Cloud console, create an OAuth client of type **Web application**.
2. Add the redirect URI `<APP_URL>/api/auth/callback/google`.
3. Set `GOOGLE_CLIENT_ID` and `GOOGLE_CLIENT_SECRET`.

## GitHub

1. In GitHub, go to **Settings → Developer settings → OAuth Apps** and create an app.
2. Set the callback URL to `<APP_URL>/api/auth/callback/github`.
3. Set `GITHUB_CLIENT_ID` and `GITHUB_CLIENT_SECRET`.

BugBerry asks for `read:user user:email` and uses a verified email whose domain is allowed, so a work email added as a secondary email on GitHub still works.

## GitLab

Works with gitlab.com and with your own GitLab.

1. In GitLab, go to **User Settings → Applications** (or **Admin → Applications** for an instance-wide app).
2. Set the redirect URI to `<APP_URL>/api/auth/callback/gitlab` and the scopes to `openid email profile read_user`.
3. Set `GITLAB_CLIENT_ID` and `GITLAB_CLIENT_SECRET`.
4. For your own GitLab, also set `GITLAB_URL`, for example `https://gitlab.example.com`. Without it, gitlab.com is used.

## Company sign-in (OIDC)

People sign in with the login your company already runs: Keycloak, Microsoft Entra ID, Okta, Authentik, Google Workspace, or anything else that speaks OpenID Connect. One identity provider per server.

1. In your identity provider, create an OpenID Connect client (a "web" or "confidential" application) that uses the authorization code flow.
2. Set its redirect URI to `<APP_URL>/api/auth/callback/oidc`.
3. Set these and restart:

```bash
OIDC_ISSUER=https://id.example.com/realms/company
OIDC_CLIENT_ID=bugberry
OIDC_CLIENT_SECRET=...
# Optional: the button reads "Continue with Example SSO". Without it: "Continue with SSO".
OIDC_NAME="Example SSO"
```

`OIDC_ISSUER` is the address your provider publishes its settings under: BugBerry reads `<OIDC_ISSUER>/.well-known/openid-configuration`. Issuer, client ID and secret go together; the server refuses to start with only some of them. For a step-by-step example, see [Keycloak](/self-host/sign-in-keycloak).

BugBerry asks for `openid email profile` and needs an email address from the provider. A provider that sends none is refused; there is no fallback to a username.

**BugBerry trusts the email your provider sends.** Someone who signs in through it with the address of an existing account reaches that account, whichever method created it. So use a provider where people cannot set their own email address, and in Microsoft Entra ID make the app **single-tenant**: a multi-tenant app accepts accounts from other organizations, whose admins choose their own addresses. A provider that says an address is unverified (`email_verified: false`) is refused; one that says nothing about it, as Entra ID does, is accepted.

Signing out of BugBerry does not sign anyone out of the provider. After the first sign-in, the account is tied to the person's ID at the provider; a later change of name or email there changes nothing in BugBerry.

### SSO only

The other methods stay on until you turn them off. Remove the Google, GitHub and GitLab variables, and for email codes set:

```bash
EMAIL_SIGN_IN=false
```

That turns off signing in with an emailed code and nothing else: invitations and notifications still go out through `EMAIL_DRIVER`. Do this once company sign-in is proven to work, not in the same change.

### When the provider is down

If the provider is unreachable when BugBerry starts, BugBerry still starts, and sign-in works again once the provider is back; no restart is needed. People who are already signed in stay signed in.

If it stays down and someone must get in, turn another method on (for example `EMAIL_SIGN_IN=true`) and restart.

### A provider with an internal certificate

When the provider's certificate comes from your company's own certificate authority, give BugBerry that authority's certificate through `NODE_EXTRA_CA_CERTS`. With Docker Compose, in a `docker-compose.override.yml`:

```yaml
services:
  api:
    volumes:
      - ./company-ca.pem:/etc/ssl/company-ca.pem:ro
    environment:
      NODE_EXTRA_CA_CERTS: /etc/ssl/company-ca.pem
  api-mcp:
    volumes:
      - ./company-ca.pem:/etc/ssl/company-ca.pem:ro
    environment:
      NODE_EXTRA_CA_CERTS: /etc/ssl/company-ca.pem
```

There is no setting to skip certificate checks.

## Email and a code

People type their email and receive a 6-digit code. Choose a mail service:

<Tabs items={["Resend", "SMTP"]}>
<Tab value="Resend">

```bash
EMAIL_DRIVER=resend
EMAIL_FROM="BugBerry <no-reply@example.com>"
RESEND_API_KEY=...
```

</Tab>
<Tab value="SMTP">

```bash
EMAIL_DRIVER=smtp
EMAIL_FROM="BugBerry <no-reply@example.com>"
SMTP_HOST=smtp.example.com
SMTP_PORT=587
SMTP_USER=...
SMTP_PASSWORD=...
SMTP_SECURE=false
```

Keep the quotes around `EMAIL_FROM`: without them, the space and the `<>` break shell commands that read `.env`.

`SMTP_SECURE=true` is for servers that start TLS right away, usually on port 465.

</Tab>
</Tabs>

A code is valid for 10 minutes, with at most 5 attempts and at most 5 codes per address in 10 minutes; in production there is also a limit per IP. Addresses outside the allowed domains never receive a code.

Without `EMAIL_DRIVER`, email sign-in is off in production. During development, codes are printed to the server log instead.

`EMAIL_DRIVER` also sends invitations and notifications. To keep those and turn off signing in with a code, set `EMAIL_SIGN_IN=false`.

## Who may sign in

```bash
ALLOWED_EMAIL_DOMAINS=example.com,example.co.id
```

- **Empty (the default):** anyone can sign up and gets a workspace of their own.
- **Set:** only those domains can sign in. New employees still need an invitation to the company workspace; without one, they get an empty workspace of their own.

## When someone leaves

The "verified" mark on an email at GitHub and GitLab doesn't go away when a work mailbox is shut down. Someone who once verified their work email on a personal GitHub or GitLab account can still sign in through that button, and `ALLOWED_EMAIL_DOMAINS` lets them in, because the address is still on your domain.

When someone leaves, remove them from your workspaces on the **Members** page. That ends their access to workspace reports, but not everything:

- **Internal** reports stay open to anyone signed in with your company's email domain, member or not, so a former employee who can still sign in can open their share links.
- BugBerry has no button to delete an account.

For a company server, prefer sign-in methods your company controls: company sign-in stops working when the account is disabled at your identity provider, and Google (with Google Workspace) or email codes stop working when the work mailbox is shut down. If you turn on GitHub or GitLab, use **Workspace** rather than **Internal** for sensitive reports.
