---
title: Account limits
description: Cap what ordinary accounts keep on a server that's open to everyone.
---

A company's own server usually wants no limits, which is the default. A server open to anyone can cap what each account keeps.

```bash
ACCOUNT_LIMITS=true
LIMIT_SCREENSHOTS=5
LIMIT_RECORDINGS=5
LIMIT_OWNED_WORKSPACES=1
LIMIT_RECORDING_SECONDS=120
```

With `ACCOUNT_LIMITS=true`, an account owns at most `LIMIT_OWNED_WORKSPACES` workspaces and can't add members to them. Each workspace keeps at most `LIMIT_SCREENSHOTS` screenshots and `LIMIT_RECORDINGS` recordings, and takes recordings up to `LIMIT_RECORDING_SECONDS` long. Deleting a report frees its slot. Workspaces that are already over a limit keep everything; they just can't add more.

The limits belong to the workspace, and they follow its owner. Every report in the workspace counts, whoever sent it, and since a limited workspace takes no members, in practice that is one person's allowance. Someone with a limited account who works in an unlimited account's workspace sends there without limits, and those reports don't count toward their own workspace.

An upload in progress counts until its upload link expires. The extension shows what's left, stops a recording at `LIMIT_RECORDING_SECONDS`, and won't send a longer one (trimmed to fit, it can); the server checks the length the extension declares again either way. Storage isn't limited per account: `MAX_UPLOAD_MB` still bounds every file on the server.

## Unlimited accounts

Accounts marked **unlimited** have none of these limits, and neither does anyone working in a workspace they own:

```bash
docker compose exec api bun apps/api/scripts/set-unlimited.ts --email someone@example.com --on
```

`--off` takes it away again. Both apply immediately.

## Turning limits on

In this order, so nobody who should stay unlimited is limited in between:

1. Deploy the current version.
2. Mark the accounts that must stay unlimited.
3. Set `ACCOUNT_LIMITS=true` in `.env` and run `docker compose up -d`.
